# Membership and payments

GameStudio has a Free plan and two paid tiers, Pro and Studio. Studio is a higher individual generation allowance; it does not advertise shared team seats. The server owns membership status and quota. A browser redirect, a checkout ID, or a client-supplied plan never grants access.

Stripe checkout creates a recurring monthly or yearly subscription. Alipay checkout purchases a fixed monthly or yearly membership with no recurring debit mandate. An Alipay renewal of the same plan starts when its current prepaid period ends. Changing a prepaid plan/provider requires its current period to end. Existing Stripe subscriptions are managed or canceled rather than creating another subscription for the same account. Switching plans with prorations, coupons, trials, or manually paid invoices is not enabled by this product.

## Configuration

Production requires `NODE_ENV=production`, an HTTPS `APP_BASE_URL` containing only the public origin, the persistent identity SQLite database, and a single application instance on a persistent volume. Back up the SQLite database together with project data. Payment webhook routes must be publicly reachable through HTTPS, with their request bodies preserved. Mount billing routes after session lookup and before any global `express.json()` middleware.

All credentials stay in server environment variables. A missing provider credential or plan price disables that checkout and returns `503 PAYMENT_PROVIDER_UNAVAILABLE`; no simulated purchase is issued. Configure one provider or both:

| Variable | Purpose |
| --- | --- |
| `STRIPE_SECRET_KEY` | Stripe account secret key; test keys for staging, live keys for production |
| `STRIPE_WEBHOOK_SECRET` | Signing secret of this application's Stripe endpoint |
| `STRIPE_PRICE_PRO_MONTHLY` / `STRIPE_PRICE_PRO_YEARLY` | Positive fixed recurring Stripe Price IDs |
| `STRIPE_PRICE_STUDIO_MONTHLY` / `STRIPE_PRICE_STUDIO_YEARLY` | Positive fixed recurring Stripe Price IDs |
| `STRIPE_PORTAL_CONFIGURATION_ID` | Optional safe configuration ID; subscription updates must be disabled and enabled cancellation must occur at period end |
| `ALIPAY_APP_ID` | Approved Alipay application ID with computer website payment enabled |
| `ALIPAY_SELLER_ID` | Merchant's receiving Alipay seller ID |
| `ALIPAY_PRIVATE_KEY` | Application RSA private key in PEM form, PKCS#1 or PKCS#8; literal `\n` is supported |
| `ALIPAY_PUBLIC_KEY` | Alipay RSA public key in PEM form, public-key integration mode |
| `ALIPAY_PRO_MONTHLY_AMOUNT` / `ALIPAY_PRO_YEARLY_AMOUNT` | CNY amount with at most two decimal places, for example `129.00`; operator sets actual prices |
| `ALIPAY_STUDIO_MONTHLY_AMOUNT` / `ALIPAY_STUDIO_YEARLY_AMOUNT` | CNY amount with at most two decimal places |
| `ALIPAY_SANDBOX=true` | Use the official Alipay sandbox gateway in staging only |
| `BILLING_FREE_MONTHLY_GENERATIONS` | Successful generations per UTC calendar month, default 5 |
| `BILLING_PRO_MONTHLY_GENERATIONS` | Default 100 |
| `BILLING_STUDIO_MONTHLY_GENERATIONS` | Default 500 |

Stripe prices are fetched from Stripe, validated against their interval and immutable price amount, and displayed in the actual Stripe currency. Public price reads are coalesced and cached, including failures, to bound anonymous provider requests. Configure quantity-one licensed fixed prices without coupons, trials, tax additions, metered items or prorations. With no explicit portal ID, the application creates its own non-default Stripe portal configuration with invoices, payment methods and customer contact/tax updates enabled, cancellation at period end enabled, and subscription plan updates disabled. Its ID is stored under a one-way key/origin/policy fingerprint and reused after restart. The application never changes the merchant's global default configuration. An explicit or cached configuration is re-fetched before creating every portal session; inactive configurations, enabled plan updates or immediate cancellation fail closed. Customers can still cancel renewal directly in GameStudio if a portal configuration is unavailable. Configure your billing contact/refund policy in the payment-provider dashboards before launch, and keep staging/test and live payment credentials on separate data volumes.

Stripe REST requests pin `Stripe-Version: 2024-06-20`. The notification body can use a newer snapshot version: notification resource IDs are retrieved again with the pinned version before the application reads membership fields. This avoids trusting outdated snapshots when notifications arrive out of order.

Register `https://YOUR_ORIGIN/api/billing/webhooks/stripe` for these events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed`, `charge.refunded`, `refund.created`, `refund.updated`, `charge.dispute.created`, `charge.dispute.closed`. Receive account snapshot notifications, not Stripe Connect or organization notifications. Configure the Alipay payment notification URL as `https://YOUR_ORIGIN/api/billing/webhooks/alipay`; checkout requests also supply this URL and the application return URL.

## Settlement and recovery

SQLite stores account-to-Stripe-customer mappings, checkout orders, paid invoice periods, subscription status, refund/dispute observations, processed notification IDs and job reservations. Mutations use synchronous `BEGIN IMMEDIATE` transactions. Checkout has a durable per-user idempotency key; retries return the original order and retain its immutable price/amount/currency snapshot even if configuration changes after a failed provider request. Notifications are acknowledged only after their verified state changes and event ledger are persisted. Retrying an event cannot grant another period. Provider synchronization is serialized within the supported single instance so an older in-flight response cannot overwrite a later cancellation or refund response.

Stripe callbacks verify HMAC-SHA256 against the exact raw body, support multiple `v1` signatures during secret rotation, and reject timestamps more than five minutes away. A subscription must match the server-created order, stored customer, user metadata, configured price and quantity. Its invoice must be settled through Stripe, have the expected amount/currency/line item, and contain a valid paid period. An unpaid, trial-only, manually marked paid or mismatched invoice cannot grant the paid plan. Cancellation at period end keeps already-paid access through its expiry; a canceled, unpaid, paused or otherwise ineligible subscription cannot grant access. Failed renewal receives no new period; an existing paid period can finish while Stripe is `past_due`.

Alipay requests and callbacks use RSA2/SHA-256. Callback verification checks the app and seller IDs as well as the signature and exact order amount. The server then queries the transaction using a signed request and verifies the signature over the exact response JSON bytes. Only `TRADE_SUCCESS` and `TRADE_FINISHED` grant a period; callback text cannot override a queried pending state. Checkout links include a signed absolute `time_expire` fifteen minutes after creation; reopening an old link cannot extend it. An unopened checkout can be canceled locally after both query and close verify `ACQ.TRADE_NOT_EXIST`; a previously copied link still has its original gateway deadline, and any actual payment confirmed within that deadline is handled as a real paid order. A full refund appears as `TRADE_CLOSED` in the official transaction query. Partial refund totals are recorded from RSA2-signed `refund_fee` notifications; transaction query has no `refund_amount` field. A full refund revokes its specific paid period; partial refunds retain the original access period. Stripe disputes suspend their specific invoice; `won`, `warning_closed` and `prevented` restore only an unrefunded original paid period. Refund tombstones prevent a late paid notification from reactivating refunded access. Refunds issued in a provider dashboard do not implicitly cancel a Stripe subscription; operators cancel future renewal separately when their refund policy requires it.

An authenticated order poll queries the provider, recovering a checkout whose notification was missed. Background reconciliation checks up to five stale active/pending orders per minute with a fifteen-second batch deadline and a five-second abort deadline per background order. It holds the synchronization lock for one order and yields between orders so notifications and account requests do not wait behind an entire batch. An order is refreshed at most once per ten minutes. This also catches canceled Stripe subscriptions or fully refunded Alipay transactions. Provider failure leaves membership based on its already-paid expiry and retries reconciliation; it does not invent a payment. Logs contain an order ID and an error code, without keys, callback bodies or buyer identities. On shutdown, `await billing.close()` stops scheduling, aborts provider requests and drains current operations before the identity database closes. A closed ledger rejects late reads/writes with `BILLING_CLOSED`, even if a provider response arrives after shutdown.

The public API keeps its UUID order IDs. New Alipay `out_trade_no` values use a separately persisted `gs_` plus the UUID without hyphens, matching the provider's letters/digits/underscore format. Page payment, transaction query, close and notification lookup all use this immutable unique merchant reference. Schema migration preserves a legacy reference already issued to a provider; an unpublished legacy order receives the corrected format before its first checkout. This prevents migration from orphaning previously issued payment URLs or changing a reference during an idempotent retry.

For cancellation of a completed Checkout whose first invoice is still unpaid, the service re-fetches the owned session, subscription, invoice and PaymentIntent, validating identity, amount, currency and price before mutating anything. A finalized unpaid invoice is voided, which cancels its invoice-owned PaymentIntent and disables the hosted invoice payment link. The service verifies cancellation before ending the unpaid subscription with `invoice_now=false` and `prorate=false`. It does not try to expire a completed Checkout or directly cancel an invoice-owned intent. A payment in `processing`, or a succeeded payment whose invoice has not settled, returns `409 PAYMENT_PROCESSING` with a wait/recheck instruction and no financial cancellation mutation. Draft/incomplete provider state is also rechecked before irreversible operations. If payment settles while an expiry/void request is being made, the service re-fetches resources once, credits the verified paid period, and cancels future renewal at period end instead of revoking paid access. An unconfirmed provider error never becomes a locally invented canceled or expired payment.

## Generation allowance

`reserveUsage(userId, jobId)` reserves one generation synchronously before a queued job mutates a project. The same immutable job ID cannot be reused by a different user or after release. Concurrent requests count both queued reservations and successes, so they cannot overrun the monthly limit. `settleUsage(jobId, 'succeeded')` consumes one generation. Failure or cancellation releases it exactly once. A successful game that is later deleted still consumed its generation. A failed enqueue must release its reservation. Generation quota resets at the first instant of the next UTC calendar month, with no rollover; annual membership receives the plan's monthly allowance rather than an annual lump sum.

After queue recovery at startup, pass all authoritative job records to `reconcileUsage(jobs)`. Terminal jobs settle their reservations; jobs missing from the recovered store release an abandoned reservation; live queued/running jobs retain theirs. Never release a reservation solely because its timestamp is old. A payment/plan change does not cancel a generation that already reserved its allowance.

## API and verification

Public `GET /api/billing/plans` reports actual configured providers and prices. Authenticated routes are `GET /api/billing/status`, `GET /api/billing/history`, and `GET /api/billing/orders/:id`. Checkout accepts `POST /api/billing/checkout` with `{provider, planId, interval}` and an `Idempotency-Key` header. State-changing routes require the session CSRF token. `POST /api/billing/portal` opens the user's verified safe Stripe portal; `POST /api/billing/orders/:id/cancel` expires an unpaid checkout or schedules a paid Stripe subscription's cancellation. Order responses include the owned subscription ID, its server-confirmed status and `cancelAtPeriodEnd` flag so the membership page can confirm cancellation without relying on the portal. Cancellation sets `cancel_at_period_end=true` and verifies the provider response before updating the ledger; a new action nonce prevents an old cached response from being replayed after a user resumes renewal. Alipay periods expire without renewal. A return URL only opens the membership page; authenticated polling confirms settlement. Orders and payment history are scoped to their owner's user ID.

`tests/billing/billing.test.js` exercises real HMAC/RSA signatures against injected provider fixtures, provider requests, identity/amount mismatches, unpaid/renewed/expired memberships, duplicate/out-of-order notifications, refunds/disputes, quota concurrency, SQLite restart recovery, cached prices, missed-notification recovery, authentication/CSRF and raw HTTP callbacks. Fixtures cannot charge money: every provider request is intercepted by the test's fetch function. Provider staging tests with your merchant keys remain the final deployment check: pay a real test-mode checkout, confirm entitlement after notification, replay the notification, cancel at period end, issue a test refund, and confirm access is revoked. Do not describe a live payment as verified until it has actually been completed in the configured merchant account.
